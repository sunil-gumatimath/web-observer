# End-to-End Code Review — Web Observer

**Date:** 2026-08-30
**Scope:** Full repository — backend (FastAPI), frontend (Next.js), infra, migrations, docs
**Verified state at review time:** git tree clean @ `86d34ed`; backend `120 passed, 2 skipped, 8 deselected`; frontend `tsc --noEmit` clean; no local Postgres/Redis running.

---

## Verdict

This is a genuinely well-built project — materially better than the median codebase of this size. The
security-critical paths (SSRF, idempotency, concurrency, multi-tenant authorization) are not
afterthoughts; they are the most carefully written code in the repo. Several decisions here are the
kind you only make after having been burned: IP pinning to defeat DNS rebinding, an atomic
conditional-UPDATE claim to make at-least-once delivery safe, and a frontend that is deliberately
wired to *fail closed* rather than fall back to a dev token in production.

The problems are concentrated in **operational hardening and drift**, not in design: the production
safety guards are unreachable by default, and the tests that verify the core correctness guarantees
are excluded from the documented test command.

| Area | Assessment |
|---|---|
| Architecture & separation of concerns | Strong |
| SSRF / fetch security | Strong — best-in-class for this project type |
| Authorization / multi-tenancy | Strong, no gaps found |
| Concurrency & idempotency | Strong |
| Crypto & secret handling | Adequate, one real gap (see M2) |
| Test coverage & CI confidence | **Weak** — the important tests don't run (see H1) |
| Production hardening | **Weak** — fail-open default (see H2) |
| Docs / infra consistency | **Drifting** (see M4, M5) |
| Data model | Solid, minor integrity gaps (see L1) |

## High severity

### H1 — The tests that verify core correctness are excluded from the documented test run

`README.md` documents:

```
pytest tests -q -m "not integration"
```

That deselects all 8 tests in `tests/test_pipeline_integration.py`, which are precisely the ones
covering the behavior that makes this product trustworthy:

- `test_first_success_is_baseline_no_change`
- `test_failed_run_does_not_replace_baseline`
- `test_change_creates_single_event_and_outbox`
- `test_unchanged_no_duplicate_alert`
- `test_outbox_idempotency_key_unique`
- `test_retention_deletes_old_snapshots`
- `test_quota_blocks_when_exceeded`
- `test_snapshot_stores_text_object_key_and_truncates_db_preview`

They are skipped twice over: excluded by the marker, *and* `conftest.db_session` calls
`pytest.skip(...)` when no Postgres test DB is reachable. In this environment Postgres is not
running, so the 2 "skipped" in the run are unrelated and these 8 never execute at all.

The `2 skipped` / `8 deselected` line in the README's "verified end-to-end" claim is therefore
doing a lot of quiet work. **A duplicate-alert regression or a quota bypass would not be caught.**

**Fix (in order of leverage):**
1. Add a CI job with a Postgres service container and run `-m integration` there. This is the
   only fix that actually closes the gap.
2. Failing that, make the pipeline tests run against in-memory SQLite. Most of them don't need
   Postgres semantics — the one that does is the idempotency test (`uq_outbox_idempotency`).
3. Until then, soften the README claim so it doesn't overstate what's verified.

### H2 — Production safety guards are unreachable because `APP_ENV` defaults to `development`

`app/config.py`:

```python
app_env: str = "development"

@property
def is_development(self) -> bool:
    return self.app_env == "development"
```

and

```python
if not settings.is_development:
    if settings.internal_api_token == "dev-internal-token":
        raise RuntimeError(...)
    if settings.secret_key == "change-me-in-production":
        raise RuntimeError(...)
```

Every production guard in the codebase fires **only when someone opts out of the default**. A deploy
that forgets to set `APP_ENV=production` silently gets:

1. **No token/secret validation.** `INTERNAL_API_TOKEN` may still literally be `dev-internal-token`,
   which grants owner-equivalent access to every workspace via `X-Internal-Token` — including
   `/internal/seed`.
2. **`Base.metadata.create_all()` at startup** (`main.py:33`), which is the exact silent schema drift
   the comment directly above it warns about.
3. **No fail-closed guard on the random `secret_key`** (see M2).

Compounding this: **`APP_ENV` is documented nowhere.** `grep` finds it in `.env.example`,
`config.py`, and `main.py` — and in **zero** files under `docs/`. The README's `backend/.env`
template lists `DATABASE_URL`, `REDIS_URL`, `STORAGE_BACKEND`, `INTERNAL_API_TOKEN`, and the Clerk
vars — no `APP_ENV`. So a careful operator following the README top to bottom still lands in
development mode in production.

**Fix:** Invert the default posture. Validate that `APP_ENV` is *explicitly set* in production
rather than inferring safety from it, e.g. fail startup when `SECRET_KEY` or `INTERNAL_API_TOKEN`
still hold their generated/dev values regardless of `app_env`. And add `APP_ENV=production` to the
README's production env template.

## Medium severity

### M1 — Outbox insert can raise an unhandled `IntegrityError` and poison the run

`app/services/pipeline.py:693` builds each outbox row with a unique idempotency key:

```python
idempotency_key=f"run:{change.run_id}:change:channel:{channel.id}",
```

backed by `UniqueConstraint("idempotency_key", name="uq_outbox_idempotency")`. The insert is a bare
`db.add(...)` + `db.flush()` — no `ON CONFLICT DO NOTHING`.

The `run_guard` claim guard (rowcount == 1) protects the *run* from double-processing, but the
outbox key is scoped to run+channel, so any path that reaches `_queue_notifications` twice for the
same run — a Dramatiq redelivery landing after a partial commit, or the async-enrichment path in
`_create_change_event` re-entering — hits a constraint violation.

That exception surfaces in `run_guard`'s `except Exception` branch, which marks the run
`internal_error` and **re-raises**. Dramatiq then retries, and the retry deterministically fails the
same way: a poison pill that burns all 3 `max_retries` and marks a healthy check as failed.

**Fix:** `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING id`, and treat a missing
return as "already queued."

### M2 — `SECRET_KEY` is a random per-process value, and that is not treated as a production failure

```python
secret_key: str = Field(default_factory=lambda: secrets.token_urlsafe(32))
```

`secret_key` derives *both* the Fernet key for BYO workspace secrets (`crypto.py:28`) and the HMAC
key for API-key hashing (`api_keys.py:20`). Because it's generated per process when unset:

- Every restart makes all `llm_api_key` / `resend_api_key` ciphertext undecryptable.
  `decrypt_secret` returns `None` and logs a warning — so AI summaries and per-workspace email
  silently stop working with no user-visible error.
- Every restart invalidates **every** `mtw_` API key hash (silently 401-ing all of them).

The guard in `get_settings()` only rejects the literal `"change-me-in-production"`, which the
`default_factory` can never produce — so the guard can never fire for this case. Combined with H2
(the guard only runs when `app_env != "development"`), a production deploy with a missing
`SECRET_KEY` passes all validation and degrades later.

**Fix:** Detect the ephemeral case explicitly (e.g. a sentinel attribute on the generated value) and
refuse to start outside development, rather than relying on a string comparison that can't match.

### M3 — Blocking outbound network calls in the request path

`create_monitor` (`monitors.py:247`) calls `fetch_brand_info(monitor.url)` synchronously — a full
outbound HTTP fetch to a user-supplied URL — before returning the response. A slow or hanging target
blocks a uvicorn worker thread for the duration. The endpoint is limited to 20/min, but that's 20
concurrent multi-second stalls. `enrich_monitor_brand` has the same shape.

Branding is explicitly optional enrichment (the code says so: "Must never fail monitor creation").
It should not be in the request path at all.

**Fix:** Return the monitor immediately and enqueue the brand fetch as a Dramatiq job.

Related: `_queue_notifications` (`pipeline.py:652`) calls `capture_screenshot()` — Playwright in a
subprocess, up to 30s — inside the change pipeline, and re-fetches a page that was fetched moments
earlier. It's non-fatal by design (good), but it holds DB work and blocks the check worker.

### M4 — Documentation has drifted from the schema

- README states "the DB schema is at migration `006_alerts`". Head is actually
  `009_add_brand_workspace_keys`. The chain is linear and correct
  (`001 → 002 → … → 009`, verified), but the README is three migrations behind.
- README instructs running `backend/scripts/apply_007.py` manually to apply newer columns, while
  `009_add_brand_workspace_keys.py` exists as a real Alembic migration. **Two competing
  schema-application paths** is how drift becomes an outage. Pick one (Alembic) and delete the
  `apply_*.py` scripts.
- `docker-compose.yml` provisions `minio` + `minio-init` and passes `S3_ENDPOINT_URL` to three
  services, while the README says snapshots are local-disk and "Docker / MinIO: Not required".
  Compose starts a service nobody uses.

### M5 — Stray and orphaned artifacts

- `backend/alembic/versions/__pycache__/009_domain_guard_state.cpython-311.pyc` has **no
  corresponding `.py`** — a deleted migration leaving a compiled artifact behind. Harmless today,
  but it will cause a confusing "duplicate revision" failure the moment a migration with that name
  is legitimately reintroduced. Clear the `__pycache__`.
- `backend/test_gemini.py` sits at the backend root, outside `tests/` — never collected, never
  cleaned up.
- `backend/scripts/` mixes real tooling (`apply_006.py`, `apply_007.py`, `e2e_smoke.py`) with
  one-off debug probes (`_check_hn.py`, `_probe_run.py`, `_fingerprint.py`, `_who_consumes.py`,
  `_verify_latest.py`, `debug_hn.py`). The underscore-prefixed ones look like scratch work from a
  debugging session and should move to a scratch dir or go.

### M6 — `list_monitors` does an unbounded scan of all change events

`monitors.py:114`:

```python
recent = db.scalars(
    select(ChangeEvent)
    .where(ChangeEvent.workspace_id == workspace_id)
    .order_by(ChangeEvent.monitor_id, ChangeEvent.created_at.desc())
    .distinct(ChangeEvent.monitor_id)
).all()
```

No `LIMIT` — this reads every change event the workspace has ever produced on every dashboard load,
to display one badge per monitor. Fine at 25 monitors; it degrades linearly with history and is the
first thing to fall over as the dataset grows.

**Fix:** A `LATERAL` join or window function taking the top-1 per monitor, bounded by the monitor
count.

## Low severity

### L1 — Missing foreign keys on a few columns

`Snapshot.run_id` is a plain nullable `UUID` with no `ForeignKey`, unlike its sibling `monitor_id` /
`workspace_id`. Same for `WebhookDelivery.workspace_id` (indexed but no FK),
`AuditLog.actor_user_id`, and `ShareLink` / `WorkspaceInvite.created_by_user_id`. Referential
integrity for those is application-managed only. Low risk, but worth a migration if you want the DB
to enforce it.

### L2 — CORS is looser than necessary

`main.py:62` sets `allow_methods=["*"]`, `allow_headers=["*"]`, `allow_credentials=True`. The
origin list is env-driven and defaults to localhost, so this is acceptable in practice — but
narrowing methods/headers to what the API actually serves costs nothing.

### L3 — Healthchecks use `pgrep -f` patterns that can match themselves

`docker-compose.yml` uses `pgrep -f 'app.scheduler'`, `pgrep -f dramatiq`, `pgrep -f 'digest_job'`.
`pgrep -f` matches against full command lines and can match the healthcheck's own shell, so these can
report healthy when the real process is dead. Misleading in production. Prefer a real readiness probe
(the API already has `/ready`).

### L4 — Implicit shared mutable state in the auth dependency

`require_workspace_member` and `require_role` mutate `principal.role_hint` as a side effect. This
works because FastAPI caches dependencies per request, but it's non-obvious coupling across three
functions. Worth a comment or an explicit return value.

Related: `get_current_principal` calls `db.commit()` to persist `last_used_at` / user upsert. A
dependency performing writes means every authenticated request implicitly commits whatever else is
pending on that session. The inline comment shows this was considered; noting it as a smell, not a
confirmed bug.

### L5 — MinIO dev credentials as defaults

`s3_secret_key` / `s3_access_key` default to `minioadmin`. Harmless given `STORAGE_BACKEND=local` is
the default, but if someone flips to `s3` and forgets to set credentials, it silently uses
well-known defaults.

## What is genuinely good

Worth calling out explicitly, because these are easy to get wrong and this project gets them right:

**SSRF defense is the strongest part of the codebase.** `PinnedIPTransport` resolves and validates
once, then pins the TCP target to the validated IP while preserving the original `Host` header and
TLS SNI — which closes the DNS-rebinding / TOCTOU window that naive "validate then fetch"
implementations leave open. Every redirect hop is re-validated. Cloud metadata
(`169.254.169.254`), link-local, loopback, and RFC1918 are all blocked. `verify=False` appears
nowhere in the codebase, and there's a custom SSL context that loads the Windows system CA store.
This is above the bar for a project of this size.

**Idempotency is enforced at every layer, not just one.** Unique constraints on
`monitor_runs.idempotency_key`, `change_events.run_id`, `notification_outbox.idempotency_key`, and
`webhook_deliveries.idempotency_key` — plus the atomic conditional `UPDATE ... WHERE status IN
(scheduled, queued)` claim in `run_guard.py:117`, which is the correct way to make Dramatiq's
at-least-once delivery safe. The `redeem_invite` flow uses the same rowcount technique to cap
`max_uses` without overshooting under concurrency. Most projects get one of these; you got all of
them.

**The frontend fails closed.** `config.ts:20` — `useClerkAuth` returns true whenever Clerk is
configured *or* when not in dev mode. `proxy.ts:27` runs `clerkMiddleware` in production even
without a publishable key. The comments explain the reasoning precisely: falling back to a shared
internal token in production would expose every workspace. This is a deliberate, correct security
decision, and it's rare to see it stated this clearly.

**Authorization has no gaps.** I checked all 60+ routes: every workspace-scoped endpoint carries an
explicit `require_role(...)` or `require_workspace_member`. Only `/billing/plans` and the public
share/invite/asset routes are unauthenticated, all by design. Non-members get 404 rather than 403,
which prevents workspace enumeration. `upsert_clerk_user` explicitly refuses to attach a Clerk
identity to an email already linked to a different account — blocking a real account-takeover path.

**Credentials are stored properly.** API keys are HMAC-SHA256 keyed with the server secret (not a
bare hash). Share and invite tokens are SHA-256 hashed at rest with only a prefix stored. Internal
token comparison uses `hmac.compare_digest`. Webhooks are signed with a timestamped HMAC.

**No SQL injection surface.** Zero string-interpolated SQL — everything is SQLAlchemy ORM/Core with
bound parameters, including the bulk delete statements.

**Resource limits are enforced before buffering.** The fetcher streams the body and enforces
`max_response_bytes` *before* accumulating it, rather than reading everything and checking after.
Redirects are capped. Response text is capped at 1M chars before diffing.

**Bot-challenge detection prevents snapshot poisoning.** `detect_bot_challenge` catches Cloudflare
interstitials and fails the run with an actionable message instead of recording the challenge page as
real content — which would otherwise produce a garbage baseline and false positives forever.

**The scheduler is multi-instance safe.** `FOR UPDATE SKIP LOCKED` with a 60s lease, per-instance
ownership, and jitter. Plus a run reaper for stuck runs, a per-domain circuit breaker and
concurrency limiter, and adaptive interval stretching. This is production-grade operational thinking.
